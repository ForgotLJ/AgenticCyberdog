# Agentic Go2 实验日报

日期：2026年10月24日，时间均为北京时间。实验记录覆盖约10:14—18:12；对话归档截止18:13:22的日报请求。设备为今天接入的新宇树Go2，不将10月20日另一台狗或小米CyberDog的结果计入今天的实测。

## 1. 今日结论

今天完成了**新Go2接入、狗上Codex部署、电脑代理借用、无线接入与故障恢复、已有控制代码整理，以及前进和双向转向的实机探索**。从最初临时查接口、写脚本，推进到了有动作反馈、独立停止和证据留存的控制入口。

**已取得有效运动，但尚未建立稳定、高效、可组合的控制能力。** 经典步态下直接Sport左转和右转约10°各通过一次；避障接口曾连续两次完成约半米前进，之后同配置再次无有效输出；最后一次直接Sport前进约0.496米，停止与恢复正常，但状态速度保护触发，因此严格验收未通过。前进—转向—前进组合未完成，也没有进入寻物、推球或自主导航任务。

最明确的新认识是：**控制接口的语义、当前步态和下游执行链，比单纯修改prompt更直接地影响动作效果；同时，现有准备和确认流程确实过重。** 今天不仅暴露了厂家运动链路的不确定性，也暴露了我们自己在初始化、审图、审批和报告上的效率问题。

## 3. 控制探索：从狗上自主试验到本地协调

### 3.1 上午至下午前段

上午先进行了状态读取、起立和短动作探索。最初动作幅度过小，难以现场辨认；延长到可见位移后，用户观察到先向前一小步、再向尾部移动约半米。这是当时的现场观察，不能直接推导为所有里程计都不可信。后续用户明确反馈：狗上Codex对身体操作相对准确，里程计绝大多数情况下与观察一致，主要问题是慢和间歇无效输出。

随后提供并上传了自主实验交接包，包含接口、已知状态、运动约定、停止方式、官方资料、脚本及历史异常，27个文件传输校验一致。狗上Codex继续开发`go2_control.py`、序列调度、点云分析和控制来源诊断。用户转贴的早期完整会话报告了约**0.485米前进、11.8°转向的环境点云配准证据**，但重复序列未通过；这部分原始狗上运行目录目前未全部取回，因此本日报将其标为远端会话报告，不能与后续已取回原始日志的实测等同。

这阶段建立了`/home/unitree/agentic_go2/body_control`工程，并发现正常动作之间夹杂大量开发、查日志和点云配准，导致一次有效操作可能间隔数分钟。于是形成下一轮效率改进方案：以相对里程计/IMU作短动作反馈，点云配准退出正常结果返回的关键路径，分阶段计时，优先复用已有CLI。

中途发生红灯/起立失败：狗上回报仅试起立一次，未继续前进或转向；当时温度字段偏高。之后红灯消失、电机错误码恢复为0，但红灯具体根因没有确定，不写作已定位并修复硬件故障。

### 3.3 今天确认的接口事实

1. 当前官方V2借用`SportModeState.error_code`表示运动状态：100为灵动，2010为经典，1001为阻尼；旧`mode=0`不能单独用来判断机器人静止或未进入运动状态。
2. `Move()`是持续速度请求、采用no-reply；返回0不等于已经运动，更不等于到达目标。应分别记录请求、下游输出和实际反馈。
3. 避障路径可以在纯yaw输入下产生平移；已观察到发布来源一致，但内部目标、代价图和仲裁原因仍未知。
4. 经典模式加直接Sport取得双向转向成功；这支持当前实现可用，不足以解释全部历史失败。
5. v8将看门狗从读取父进程文件改为直接订阅`rt/utlidar/cloud_base`。本次运动记录62个通畅几何样本，最大检查年龄0.108s，提供了在运动中持续新鲜的证据。
6. 0.3001m/s下游指令界限、0.50m/s状态速度异常界限都是本实验阈值，不是厂家额定极限。两类速度不能混用。

用户关于“动作效率差、约束太多”的反馈成立。此前为了保持单变量试验和限定授权，反复形成候选、单次确认、逐段审图；此外，每次动作都重新启动发送器、看门狗和四个停止子进程，再串行采集状态并固定等待。这些开销叠加，造成很长的实验间隔。曾发生图像审阅超时，批次没有发出任何运动就结束；这属于流程失败，而不是机器人运动能力失败。

今日最后在电脑上形成**v9准备流程精简候选**：

- 并行进行工作进程启动、状态订阅和通道检查，移除固定1秒等待。
- 将连续0.5秒通道检查与启动重叠，不在启动后再重复等待。
- 图像/原始点云归档改为按需；实时状态、点云判断和停止路径保留。
- 删除归档额外0.8秒等待，终端只返回一行最终结果，完整日志仍可追查。

4项新增逻辑测试和Python语法检查通过。**因SSH掉线，v9未上传、未完成狗端回归或只读计时，更未实机运动；不能宣称实际提速已经达成。** 常驻执行会话尚未实现，不把“提出复用DDS”写成已交付能力。

## 5. Agent架构与sim2real调研

今天重新阅读RoboDawn主页、harness说明和适配代码，明确其核心不是把LLM装到机器人上，而是组织统一观察、动作接口、执行反馈、坐标参考和闭环记忆。我们决定借鉴其接口组织方式，让Codex继续承担探索、编程和任务决策，高频控制与停止由本地执行层承担。

本地另一条对话完成Go2仿真环境资料核查，形成独立比较文档：

| 方向 | 调研结论 |
| --- | --- |
| 官方`unitree_mujoco` | Go2模型与SDK2低层通信明确；默认示例不等于完整高层行走/避障服务 |
| 官方`unitree_rl_lab` / Isaac Lab | 有Go2速度跟踪训练与部署路线，需要控制策略和版本匹配 |
| 社区`rl_sar` | 有Go2策略文件和维护者仿真/真机支持记录，可优先考察快速行走原型；不是本项目已复现 |
| NaVILA / VLN-CE-Isaac | 有Go2导航任务与评测协议，更接近后续语言导航benchmark |

今天没有安装运行仿真器，没有进行sim2real迁移，也没有执行正式benchmark。当前顺序仍是：先获得可靠且高效的真机动作接口与最小观察反馈，再在仿真中迭代相同harness，冻结后回真机比较。应明确仿真控制器与真机原厂控制器的差异，避免把底层控制差别误算成agent能力变化。
